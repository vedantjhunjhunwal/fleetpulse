# FleetPulse requirements

Each requirement has an ID. Tests name the requirements they verify with a
`REQ:` comment, and `tools/trace.py` fails the build if any requirement has no
test (see [TRACEABILITY.md](TRACEABILITY.md), generated by the same script).

## Functional requirements

| ID | Requirement | Component |
|---|---|---|
| FR-01 | Parse candump log lines (timestamp, vehicle/interface, 29-bit identifier, 0–8 data bytes) and reject malformed lines without stopping. | C decoder |
| FR-02 | Derive priority, PGN and source address from a 29-bit identifier, treating PDU1 (PF < 240) destination addresses correctly. | C decoder |
| FR-03 | Decode engine speed (SPN 190), vehicle speed (84), coolant temperature (110), fuel rate (183), fuel economy (184), fuel delivery pressure (94) and oil pressure (100) with J1939-71 resolution and offset. | C decoder |
| FR-04 | Treat raw "error", "not available" and reserved values as missing, never as numbers. | C decoder |
| FR-05 | Decode DM1 active trouble codes: 19-bit SPN, FMI, occurrence count, lamp status, and the "no active DTC" broadcast. | C decoder |
| FR-06 | Reassemble multi-packet messages sent with BAM (TP.CM / TP.DT), per vehicle and source address, rejecting out-of-order packets, inconsistent announcements and gaps over 750 ms. | C decoder |
| FR-07 | Accept a candump log over HTTP, decode it through the C library and report lines, frames, events, malformed lines, transport errors and BAM messages. Re-sending a day replaces it. | .NET API |
| FR-08 | Aggregate each truck's day: distance, fuel used, km/L, idle share, engine hours, cruise and high-load coolant temperature, fuel-pressure statistics, oil pressure and trouble-code counts. | .NET API |
| FR-09 | Track each trouble code's lifecycle per truck (first/last seen, cleared, returned) and describe it (component, failure mode, system, major or minor). | .NET API |
| FR-10 | Export the daily summaries as CSV with a fixed column set for the analytics. | .NET API |
| FR-11 | Predict the probability that a truck has a major cooling or fuel-system fault within 7 days, evaluated with cross-validation grouped by truck, and report warning time and false alerts. | R analytics |
| FR-12 | Accept risk scores, band each truck (fault active / high / watch / normal / not scored) and produce a ranked maintenance queue with the workshop action for the system at risk. | .NET API, R |
| FR-13 | Dashboard: fleet KPIs and a truck table ordered by urgency. | Angular |
| FR-14 | Dashboard: per-truck trends of the fault indicators, with fault days marked, and the truck's trouble codes. | Angular |
| FR-15 | Dashboard: maintenance queue with status, risk, system, action and active faults. | Angular |
| FR-16 | Reject invalid input with RFC 9457 problem details (wrong media type, empty body, no valid frames, unknown truck, invalid risk scores). | .NET API |

## Non-functional requirements

| ID | Requirement | How it is checked |
|---|---|---|
| NFR-01 | The decoder sustains at least 1 million frames per second on one core. | `tools/check_bench.sh` |
| NFR-02 | The decoder has no memory or undefined-behaviour errors. | C tests under AddressSanitizer + UBSan in CI |
| NFR-03 | Every requirement is covered by at least one test. | `tools/trace.py` in CI |
| NFR-04 | Simulated data is reproducible from a seed. | simulator tests |
